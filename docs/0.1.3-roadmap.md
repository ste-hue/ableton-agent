# Tembro 0.1.3 — roadmap and lessons from the first real beta session

Distilled from the 2026-08-31 session: the day 0.1.2-beta went from a grey
rectangle to a shipped, verified product. Everything here was observed on a
real machine with real Ableton Live 12 — nothing is speculative.

## What 0.1.2-beta shipped (and verified live)

- Chat page loads reliably (js-object Task pump + `web.message("readfile", <abs>)`,
  the only readfile delivery that reaches jweb in Live's bundled Max runtime).
- node.script boots via `live.thisdevice → delay → script start` alongside loadbang.
- Stop button (`/stop`), soft 180s / hard 240s turn watchdog — a turn can never
  strand the device with `busy=true`.
- Session honesty: 401 clears `~/.tembro/session.json` and returns the page to a
  prefilled sign-in; the view is driven only by node's `auth` messages.
- Clipboard buttons (copy per reply, paste with visible failure), credentials
  remembered only after a successful connect.
- Agent prompt now teaches the LOM facts the model kept getting wrong
  (mixer_device vs Track, fire clips vs transport, bare Drum Rack is silent,
  24-step budget discipline).
- End-to-end check: `gettembro.com/v0/version` → 0.1.2-beta, release DMG
  downloads (HTTP 200), full activation → composition → credits flow works.

## 0.1.3 priorities (ranked)

1. **Knowledge base in the system prompt.** The model's failures are ignorance,
   not stupidity: it burned its 24-step budget on reads that cannot succeed.
   Distill `.agents/skills/` (beat-making, harmony-melody, song-from-scratch)
   plus the `ableton-lom` reference into a curated block served from a new
   `server/src/knowledge.ts`. With OpenAI prompt caching (cache read $0.02/M)
   a 10× richer prompt costs almost nothing. Later, when the corpus outgrows
   the prompt (~50k+ tokens): Cloudflare Vectorize + embeddings for retrieval.
   A community KB lands via PRs into `knowledge/` (first contribution pending).

2. **Stronger model + heavy credits.** Current: gpt-5.6-luna ($0.20/M in,
   $1.20/M out) ≈ $0.015 per heavy cached turn. Direction decided in session:
   *one credit must be a heavy thing.* Experiment: `LLM_MODEL=gpt-5.6-terra`
   ($2/M in) for audibly better musicianship at ~10× input cost; end state is
   a router — Luna for chat/simple commands, Terra for composition — and a
   pricing model where a credit maps to a composition, not a message.
   Beta grant stays 100; subscription target ~€12/mo but with credits priced
   per composition weight, not flat per message.

3. **Step feed in the chat (à la LiveWorks).** While the agent thinks
   (turns take 20–120s), stream every tool call into the transcript as a
   collapsible row — click it to see the call and its result. The data
   already exists (`onStatus`/`onTool` in `agent_loop.js`); it just needs a
   `steps` outlet message and UI rendering. This converts perceived slowness
   into watchable work.

4. **Continuation-token replay fix.** Tokens are valid 30 minutes with no
   single-use tracking: replay = free OpenAI calls. Add a used-token (or
   step-counter) check in D1 keyed by `requestId+step`. Required before any
   public promotion; fine for private beta.

5. **Cumulative usage logging.** `agent.completed` records only the final
   step's usage — undercounts real token spend ~20× on long turns. Sum usage
   across steps server-side; it is the input to all pricing decisions.

6. **Chat history persistence.** Transcript lives only in the page DOM and
   dies on every reload. Persist to localStorage (or ask node for a replay).

7. **Musical closure rules → code.** "Done" should mean audible when the user
   asked to hear something: fire the scene, verify `is_playing`, ensure the
   Drum Rack actually has a kit. Now prompt-enforced; codify in the executor
   and restore code-level readback (`executor.js` is currently dead on the
   v0.2 path — 17 tests test dead code).

8. **If the repo goes private:** the release DMG link dies for the public.
   Move the artifact to R2 and point `DOWNLOAD_URL` there first.

## Lessons about Live's bundled Max runtime (read before touching the device)

- Load-time events are unreliable: `loadmess`, subpatcher `loadbang`, and
  `node.script @autostart` all misfire. Anything critical must be driven by
  `live.thisdevice`, an owned `Task` pump, or node itself — never by a single
  load event.
- Patch-cord messages to jweb (loadmess or node outlet kicks) may never
  arrive; a js-object scripting call `obj.message("readfile", path)` does.
  jweb's internal server 404s absolute paths sent as *page URLs* but accepts
  absolute paths via `readfile`.
- The v8 object is not the js object: `"use strict"` + bare `inlets = 1`
  kills the whole script ("v8: no function bang" spam), and its maxobj API
  did not deliver here. The validated M4L host pattern is legacy `js` (ES5).
- Node for Max starts reliably only on the first device load of a Live
  session; delete/re-add cycles often leave node unbootable until Live
  restarts.
- The webview cannot reach the OS clipboard via ⌘C/⌘V and localStorage may
  throw: every convenience needs an in-page affordance with visible failure.
- One driver at a time is real: an external MCP session driving Live while
  the device runs its own bridge produces interleaved stalls.
